# Design — Realized Cost-Basis Rate for Bolívar Spending

**Date:** 2026-07-21
**Status:** Approved (design); implementation not started
**Supersedes decision in:** ADR-005 §1 Option 2 (previously rejected)
**Requires:** new ADR-013, amendment to `docs/architecture/rules/rule-005-single-rate-resolver.md`

---

## 1. Problem

The ledger answers "what were these bolívars worth on the day I spent them?" The owner needs it to answer "**how many dollars did this actually cost me?**"

Those diverge whenever the VES rate moves between acquisition and spending. Bolívars bought at 40 VES/USDT last week and spent this week at a market rate of 50 are currently valued at the *spend-day* rate, understating the real dollar cost by 20%.

Today `finances/domain/rates.py::resolve()` uses `txn.occurred_at.date()` for every fallback lookup — a mark-to-market model. Every bolívar expense from the bank carries `user_rate = NULL`, so it always lands on that day's `binance_p2p_median`.

The data needed to fix this already exists. Every Binance P2P trade is ingested with `user_rate = unitPrice` — the exact realized VES/USDT rate of that trade (`finances/ingest/binance.py:178`). A P2P **sell** is precisely the moment bolívars are acquired.

## 2. Decision

Insert a **realized cost-basis tier** into the resolver, between the manual override and the market median.

Three modeling decisions, chosen by the owner:

| Decision | Choice | Rejected alternatives |
|---|---|---|
| Cost-basis model | **Latest realized rate, carried forward** | Weighted-average pool; FIFO lots |
| Same-day multiple sells | **Volume-weighted average (VWAP)** | Last sell of day; median of day |
| Stale-rate handling | **14-day max age, then fall through** | No guard; flag `needs_review` |

Storage approach: **materialize per-day realized rates into the existing `rates` table** under a new source, rather than querying transactions live or adding a SQL view.

## 3. Model

For a bolívar transaction on date `D` with no manual `user_rate`:

1. Find the most recent date `A <= D` on which P2P sells occurred.
2. Use that day's volume-weighted realized rate.
3. If `D - A > 14 days`, the rate is too stale to trust — fall through to the existing market chain.

Worked example:

```text
Jul 1   sell 100 USDT @ 40, sell 50 USDT @ 44
        -> 6200 VES received for 150 USDT
        -> realized rate for Jul 1 = 6200 / 150 = 41.3333...

Jul 3   spend 6200 VES  -> / 41.3333 = $150.00   source = binance_p2p_realized_carry
Jul 15  spend 6200 VES  -> / 41.3333 = $150.00   source = binance_p2p_realized_carry  (14d, inclusive)
Jul 16  spend 6200 VES  -> falls through to that day's median   (15d, too stale)
```

## 4. Architecture

### 4.1 Derivation — `finances/domain/realized_rates.py` (new)

Single-purpose module: derive per-day realized VES rates from P2P sell transactions.

**Selecting P2P sells.** `kind` is *not* a reliable filter — bank-anchored pairing promotes these rows to `kind='transfer'` after the fact. Mirror the filter already proven in `finances/domain/transfers.py` (`SQL_BINANCE_CANDIDATES`):

```sql
source_ref LIKE 'p2p:%'
  AND CAST(amount AS REAL) < 0     -- negative = asset leaving = a sell
  AND user_rate IS NOT NULL
```

**VWAP per day**, grouped by `DATE(occurred_at)`:

```text
rate_day = Σ(|amount| × user_rate) / Σ|amount|
```

All arithmetic in `Decimal`; floats never enter the path (ADR-009). Full precision retained — no rounding at derivation time. Serialize using the same helper the rates repo already uses for `Rate.rate`.

**Upsert** one row per day into `rates`:

```text
(as_of_date=D, base='USDT', quote='VES', source='binance_p2p_realized', rate=VWAP)
```

No schema change required. `rates` already carries `UNIQUE(as_of_date, base, quote, source)`, which makes rebuild naturally idempotent.

**Public surface:**
- `compute_realized_rates(conn) -> list[Rate]` — pure derivation, no writes. Directly testable.
- `rebuild(conn) -> int` — derive + upsert, returns row count.

### 4.2 Fiat assumption and guard

The trade's fiat currency is **not stored on the transaction**. `Transaction.currency` holds the *asset* (USDT); the fiat appears only inside the generated description (`finances/ingest/binance.py:165-167`):

```text
P2P SELL USDT @ 41.33 VES (order 12345)
```

v1 assumes VES. Because the description is generated by our own code its format is deterministic, so the derivation parses the fiat token from it as a guard: **a trade whose description parses to a fiat other than VES is skipped and logged**, never folded into the VES VWAP. A trade whose description does not parse at all is treated as VES (the ledger is VES-only in practice).

Adding a real `fiat` column was considered and rejected: adding a `transactions` column breaks every hand-listed `SELECT` feeding `_row_to_transaction` across the repo, triage, monthly, and consolidated paths — disproportionate cost for a single-fiat ledger. Revisit only if a second fiat ever appears.

### 4.3 Resolver — `finances/domain/rates.py` (changed)

New tier 2. Tiers 1, 3, 4, 5 keep their current behavior exactly.

```text
1. txn.user_rate is not None
       -> (txn.user_rate, 'user_rate')

2. NEW — realized cost basis:
       r = latest_on_or_before(USDT, VES, 'binance_p2p_realized', as_of)
       if r is not None and (as_of - r.as_of_date).days <= REALIZED_MAX_AGE_DAYS:
           -> (r.rate, 'binance_p2p_realized')        when r.as_of_date == as_of
           -> (r.rate, 'binance_p2p_realized_carry')  when r.as_of_date <  as_of
       else: fall through

3. binance_p2p_median  (+ '_carry')     unchanged
4. bcv                 (+ '_carry')     unchanged
5. none -> needs_review = True          unchanged
```

New module constants: `REALIZED_SOURCE = "binance_p2p_realized"`, `REALIZED_MAX_AGE_DAYS = 14`.

**Boundary is inclusive:** age exactly 14 days uses the realized rate; 15 days falls through.

Two behaviors verified to fall out with no extra work:

- **P2P trades still value themselves correctly.** They carry `user_rate`, so tier 1 fires first — a trade is valued at its own rate, not a carried one.
- **Headline eligibility needs no report change.** `finances/reports/consolidated_usd.py:161` computes `is_bcv_fallback = source.startswith('bcv')`, so the new source counts toward the headline total automatically and is not a strict-mode violation.

**Scope of tier 2:** it applies only where the quote currency is VES, consistent with the existing hardcoded fallback tiers. It applies uniformly to VES expenses *and* VES income. For income this means "USD value of bolívars received, at your prevailing cost basis" — a deliberate simplification accepted for consistency and simplicity, since the owner's income is overwhelmingly USD-side.

### 4.4 Ingest wiring

`finances/ingest/binance.py` calls `realized_rates.rebuild(conn)` after P2P ingest completes, so realized rates stay current with no separate step.

A CLI command `finances rates rebuild-realized` exposes the same operation for the one-time historical backfill and for recovery if a P2P transaction is later edited or deleted. This is the accepted mitigation for the derived-data drift risk inherent to materializing.

### 4.5 Disposition of `v_transactions_usd`

The view (`001_initial.sql:167-200`) computes `amount_usd` in SQL using its own hardcoded `binance_p2p_median` logic. This is already a standing violation of rule-005 ("No SQL view, report, or ingester may compute `amount_usd` inline using its own rate logic"). Once tier 2 exists the view silently disagrees with the resolver.

**Decision: drop the view** (migration `012`). The Python resolver becomes the sole authority for USD valuation.

Rejected: mirroring the 5-tier chain plus VWAP and the age guard in SQL (hand-synced duplication, explicitly forbidden by rule-005); and demoting the view to a renamed "market reference" (leaves two conflicting USD answers in the database — the exact failure class this project exists to eliminate).

**The lost invariant is replaced, not discarded.** `tests/test_reports_monthly.py:412` currently asserts the monthly report's totals equal the view's totals. That cross-check is replaced by an assertion that **monthly report totals equal consolidated report totals** — two independent Python code paths, one rate implementation.

## 6. Testing

Tests land before implementation (rule-011). Coverage targets unchanged: ≥85% domain.

- VWAP: single-trade day; same-day mixed prices; verify `Decimal` precision, no float drift.
- Age guard boundary: day 14 uses realized; day 15 falls through to median.
- Chain order: manual `user_rate` beats realized; realized beats median; with no realized rates present, behavior is byte-identical to today.
- Carry labeling: exact-date hit returns `binance_p2p_realized`; older hit returns `binance_p2p_realized_carry`.
- Rebuild idempotency: running twice produces identical rows and no duplicates.
- Sell-detection: a P2P sell already promoted to `kind='transfer'` is still included.
- Fiat guard: a non-VES P2P sell is skipped, not folded into the VES VWAP.
- Zero-volume guard: a day whose sells sum to zero volume is skipped, never divides by zero.
- Replacement invariant: monthly totals == consolidated totals.
- Hypothesis properties on tier ordering and the age guard (rule-011 requires property tests for rate logic).

## 7. Rollout

1. Apply migration 012.
2. Run `finances rates rebuild-realized` to populate history.
3. Run `finances report consolidated` before and after, and diff — this shows exactly which transactions re-valued and by how much. Read-only; no writes.

Expected direction: bolívar spending that followed a sell at a lower VES rate will now show a **higher** USD cost than before.

## 8. Out of scope (YAGNI)

- Weighted-average or FIFO lot tracking — explicitly rejected in §2.
- Multi-fiat support — see §4.2.
- Cost basis for any currency other than VES.
- Backfilling a `fiat` column onto `transactions`.
- Any change to categorization, transfers, or reconciliation.
